# MySocialMedia API Compact Architecture and Method Reference

This document covers only the .NET backend. It combines a brief architecture overview,
a complete folder/file tree, the controller endpoint map, and every explicitly declared
C# method found by the C# syntax parser in the reviewed source.

## Scope

- Repository: [MySocialMedia-Api](https://github.com/abhishekgithub0610/MySocialMedia-Api).
- Commit: `56fb5fbfd051d3e83e7e0ceb3958b5ee55e34118`. Current source takes precedence after later changes.
- Inventory: **421 tracked files + 1 local file**, **102 folders**.
- Method index: **375 C# files**, **528 declarations**, **48 controller HTTP endpoint mappings**.
- Paths and line numbers are relative to this backend snapshot.
- The file tree includes assets, hidden application files, migrations, documentation
  and declared empty folders. No application directories are collapsed.
- Only the internal `.git` database is outside the application inventory.
- `[local file]` means untracked local content; `[empty folder]` includes project-declared folders.
- Method coverage includes constructors, interface methods, private/protected methods,
  overloads, local functions if present, and generated migration methods.
- Comments are not active methods. Implicit compiler-generated methods, inherited
  framework methods, lambdas and property accessors are not separate method declarations.
- This is a syntax/source analysis, not a claim that the API builds or passes runtime tests.

## Architecture at a glance

```text
HTTP → API controller → MediatR handler → repository interface → EF repository → SQL Server
                    └→ AuthService → Identity / JWT / refresh-token services
Handlers → FileService → wwwroot/images
Email service → in-memory background queue / SMTP
```

The API is one ASP.NET Core application targeting .NET 8 across six projects.

| Project                      | Responsibility                                                |
| ---------------------------- | ------------------------------------------------------------- |
| MySocialMedia.Api            | Startup, routes, controllers, middleware, DI and static files |
| MySocialMedia.Application    | Commands/queries, handlers, DTOs, interfaces and services     |
| MySocialMedia.Domain         | Entity classes, enums and entity contracts                    |
| MySocialMedia.Persistence    | EF model, repositories, unit of work and migrations           |
| MySocialMedia.Infrastructure | Files, email, refresh tokens and supporting services          |
| Shared                       | API response envelopes, errors and constants                  |

Start with `MySocialMedia.Api/Program.cs` and its `Extensions` registration files.
The EF model is `MySocialMedia.Persistence/Data/ApplicationDbContext.cs`, derived from
IdentityDbContext. Social features use MediatR; authentication primarily calls services.
Namespaces retain MySocialMedia, PandeyFurniture, Domain and Application.Core naming.
Some older commerce/activity code and placeholder classes remain; verify registration
and callers before assuming a feature is active.

## Main contracts and implementation cautions

- Normal response envelopes contain `isSuccess`, `message`, `errors`, `hasErrors` and
  generic `result`. Check controller mapping: some actions return 200 for failure envelopes.
- Uploads use multipart binding: `PageImage`, `ProfilePicture` and post `Files`.
- FileService uses `page-profile`, `user-profile`, `page-post` and `user-post` folders
  beneath `wwwroot/images`. It returns filenames; DTOs often build relative image URLs.
- Database saves vary by repository. Filesystem writes do not roll back with SQL failures.
- GlobalExceptionMiddleware is enabled and returns generic 500 errors. Its manual
  serialization differs in casing from MVC responses; the separate filter is not registered.
- Authorization/ownership and validation registration are uneven. Page-update ownership
  and new page-type EF tracking remain review targets in this snapshot.
- Page DTO/edit fields differ; user update does not assign submitted CountryCode.
- General feed visibility differs from interest suggestion filtering. Check policy explicitly.
- Identity seed runs at startup; Hangfire/health/email infrastructure is registered.
  Do not start the API against production data merely to inspect behavior.
- Comment AI moderation invocation is commented out, although its service is injected.
- A class, package or method existing does not establish runtime reachability.

## How to use the indexes

1. Find the HTTP verb/path in the endpoint table to locate the controller action.
2. Follow its command/query or service into Application and then Persistence/Infrastructure.
3. Use the method index to find exact file, declaring type, signature and source line.
4. **Internal methods have no HTTP endpoint of their own.** They can support multiple
   endpoints. The method table shows direct controller routes only, not inferred call graphs.
5. Inspect authorization, inputs, save boundaries and return DTOs before changing code.
